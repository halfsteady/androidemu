# AccuracyCoin accuracy pass

On `feat/core-accuracy`, based on `feat/portable-desktop`, the unchanged
AccuracyCoin ROM improves from **92/144 to 103/144**. All 144 tests finish;
none are skipped, and every previous pass is retained. The 41 remaining failures
are explicitly recorded, rather than counted as supported behavior.

The ROM matches upstream [AccuracyCoin revision
affc643](https://github.com/100thCoin/AccuracyCoin/tree/affc643aa771028510c4427451ecf5bba5e54592).
Its SHA-256 is
`8a563df212d8d87e53b83eb55fc1ac27a75586c25badafbadb3d63acb4b552ed`.
[Per-test before/after results](accuracycoin-results.json) include the page,
result address and hexadecimal failure code.

## Changes

- APU status reads preserve the external CPU data-bus latch and expose its
  unconnected bit 5. Writes still update the external latch.
- An NMI arriving during BRK/IRQ stack pushes can replace the interrupt vector
  without changing the pushed return address or B flag. Later edges wait until
  the first instruction of the original handler has executed.
- Sprite fetch resets OAMADDR during dots 257–320 when rendering is enabled.
  Previously a nonzero address could persist across frames and misalign later
  DMA copies, breaking sprite hits and several rendering tests.
- OAM attribute reads mask the unimplemented bits. Reads during secondary-OAM
  clearing return `$FF`; rendering-time writes preserve OAM and advance its
  address by four with the low bits cleared.
- Controller strobes latch on the APU put phase, correctly handling one-cycle
  strobes generated by read-modify-write instructions.
- Background pattern shifters shift in ones, as described by AccuracyCoin's
  BG Serial In test. Other missing background pipeline behavior still prevents
  that full test from passing.

These changes apply to both Android and desktop because both use `nes-core`.
No ROM-name detection or AccuracyCoin-specific behavior was added to the core.
State fields and the save-state format remain unchanged.

Newly passing tests: Open Bus; NMI Overlap BRK; NMI Overlap IRQ; Controller
Strobing; Sprite overflow behavior; Sprite 0 Hit behavior; Suddenly Resize
Sprite; Misaligned OAM DMA; Rendering Flag Behavior; `$2007` read with rendering;
Attributes As Tiles.

## Reproduce

Keep the ROM outside the repository. The runner boots it, presses Start through
the normal controller API, and reads its own result table after completion.
It does not patch the ROM, set its test results or skip difficult tests.

```sh
cargo run --release -p nes-runner -- accuracycoin /path/to/AccuracyCoin.nes
python3 scripts/check-accuracycoin.py /path/to/AccuracyCoin.nes --report /tmp/accuracycoin.json
cargo test --workspace --locked
python3 scripts/check-roms.py /path/to/nes-test-roms --report /tmp/rom-regressions.json
```

The runner returns 0 only for 144 passes, 1 for a completed suite with failures,
and 2 for an unsupported layout or timeout. The regression script checks the
pinned ROM hash and rejects any lost pass, skipped/unfinished test or timeout;
it permits newly passing tests. CI downloads that exact external ROM revision
for testing, without packaging it in the player.

Focused synthetic tests cover CPU open bus, interrupt hijacking and late NMI,
controller phase, OAM address reset and OAM register behavior. The existing
39-ROM CPU/APU/PPU/MMC3 regression suite is also used to check for regressions.

Validated on macOS Apple Silicon: all 97 workspace tests (including the real
nestest reference trace), all 39 external regression ROMs, the 103-pass
AccuracyCoin check, runner/desktop lint, the release build and the SDL desktop
smoke test passed. Existing save-state compatibility tests also pass.

## Remaining limitations

Most remaining failures involve DMC DMA timing and bus arbitration, APU register
timing, cycle-by-cycle sprite evaluation/secondary OAM, and PPU fetch-bus overlap.
Correcting branch interrupt polling in isolation exposes an existing DMC sync
failure in a later subtest, so that broader timing work is not included here.
The exact failure list is in the JSON report above. This is a measured accuracy
improvement, not a claim of complete hardware accuracy or PAL/Dendy validation.
